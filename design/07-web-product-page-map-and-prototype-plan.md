# 07. 网页端产品页面清单与原型方案

## 1. 这次重构要解决什么问题
当前仓库已经具备真实的认证、预约、对话、知识库和后台接口，但前端仍停留在“按接口联调拆页面”的阶段，导致：

- 登录、预约、聊天虽然能调用真实接口，但不像完整产品。
- 用户侧和管理员侧没有被拆成清晰的两套工作台。
- 登录后的去向、角色分流、左侧导航体系都没有真正建立。

这次先不急着继续绑真实后端页面，而是先把网页端产品结构定下来，再用原型稿评审方向。

---

## 2. 基于现有代码得到的结论

### 2.1 角色和权限
- 后端已经通过 `roles` 字段返回用户角色。
- `/api/v1/auth/login` 和 `/api/v1/users/me` 都能提供角色信息。
- `/api/v1/admin/**` 已经要求 `ADMIN` 权限。

结论：
- 前端可以做“统一登录页 + 登录后按角色自动分流”。
- 真实安全逻辑必须以后端返回的 `roles` 为准，而不是前端让用户自己勾选权限。

### 2.2 现有后端已经足够支撑的页面
- 用户侧：
  - 认证与账户
  - 科室 / 医生 / 号源查询
  - 预约创建 / 取消 / 列表 / 详情
  - 会话列表 / 消息列表 / SSE 对话
  - 当前用户资料与默认偏好
- 管理员侧：
  - 知识库管理
  - 会话查看
  - Agent Trace 查看
  - 审计日志查看

结论：
- 用户工作台和管理员工作台都已经有后端基础，不需要再靠假数据硬撑结构。
- 当前更缺的是页面信息架构，而不是接口能力。

---

## 3. 推荐的正式网页端信息架构

### 3.1 路由层次

### 公共层
- `/`
  - 品牌首页 / 产品介绍 / 入口分流
- `/login`
  - 统一登录页
  - 登录成功后按角色自动跳转

### 用户工作台
- `/app/dashboard`
  - 用户首页，总览预约、导诊、近期服务状态
- `/app/appointments`
  - 预约服务主工作台
- `/app/assistant`
  - 导诊助手工作台
- `/app/services`
  - 我的服务记录，聚合预约记录与对话延续线索
- `/app/profile`
  - 个人资料、默认科室、就诊偏好

### 管理工作台
- `/admin`
  - 管理后台总览
- `/admin/knowledge`
  - 知识库管理
- `/admin/conversations`
  - 会话排查
- `/admin/traces`
  - Agent Trace 排查
- `/admin/audit-logs`
  - 审计日志
- `/admin/system`
  - 系统参数与策略配置预留页

### 3.2 导航原则
- 未登录用户只看公共层。
- 登录后：
  - `ADMIN` 进入管理员工作台。
  - `USER` 进入用户工作台。
- 用户工作台和管理员工作台都采用左侧导航。
- 当前仓库已有 `/appointments`、`/chat` 这类顶级路由，后续正式开发建议收口到 `/app/*`，原路由作为兼容跳转页。

## 5. 原型稿的评审重点
这次原型不追求和后端真正联调，而是让你确认：

1. 登录分流是否合理。
2. 用户端是否应该收口为一套左侧工作台。
3. 管理端是否应该独立成一套后台壳层。
4. 页面清单是否齐全，是否还缺关键业务页。
5. 视觉方向是否更接近“完整产品”，而不是“测试页”。

## 6. 首轮原型覆盖范围

### 原型访问路径
- `/prototype`
- `/prototype/login`
- `/prototype/patient/dashboard`
- `/prototype/patient/appointments`
- `/prototype/patient/assistant`
- `/prototype/patient/services`
- `/prototype/patient/profile`
- `/prototype/admin/dashboard`
- `/prototype/admin/knowledge`
- `/prototype/admin/conversations`
- `/prototype/admin/traces`
- `/prototype/admin/audit`

### 为什么首轮原型先做这些页
- 这几页已经覆盖了“登录分流 -> 用户使用 -> 管理员排障”三条主线。
- 这些页面之间能直接验证左侧导航、角色隔离和任务组织方式。
- 它们也是后续真实开发时最值得优先投入的页面骨架。

---

## 7. 原型确认后，真实开发建议顺序

### 第一步：路由与壳层重构
- 建立统一登录分流逻辑。
- 建立 `/app/*` 用户工作台壳层。
- 保持 `/admin/*` 管理后台壳层。

### 第二步：用户工作台真实接后端
- 先做 `/app/dashboard`
- 再做 `/app/appointments`
- 再做 `/app/assistant`
- 再做 `/app/services` 与 `/app/profile`

### 第三步：管理员工作台真实接后端
- 保持现有后台能力，但按统一壳层和正式交互重做。

### 第四步：联调与验收
- 用户登录 -> 预约 -> 取消 -> 对话延续
- 管理员查看会话 / trace / 审计回放
- 如需真实 AI 能力，再由你启动后端服务做完整联调

---

## 8. 本轮结论
- 前端不该再继续做零散顶级页，而应该进入“公共层 + 用户工作台 + 管理工作台”的产品结构。
- 登录页不该只是接口联调表单，而应该承担角色分流入口。
- 用户端与管理员端都应该使用左侧导航作为主要工作区组织方式。
- 在真实后端能力已经具备的前提下，先评审原型，再进入正式开发，是当前最稳的路径。
